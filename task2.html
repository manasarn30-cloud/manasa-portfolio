Task 2 — IoT series

Adafruit IO Dashboard & MQTT

Controlling a mains bulb through a relay from a cloud dashboard using MQTT.

MQTTAdafruit IORelayESP32

Learning objectives

  • Understand MQTT publish/subscribe architecture and its QoS levels (0, 1, 2)
  • Integrate a cloud IoT platform (Adafruit IO) with an ESP32
  • Switch a high-voltage (230 V AC) device safely through an isolating relay module
  • Understand API keys and access control for a cloud service
  • Design a system that tolerates network latency and fails safe

Purpose of Adafruit IO in an IoT system

Task 1 worked only inside one Wi-Fi network. Adafruit IO is a cloud platform that gives the project a public place for data: it stores values in feeds, shows them on a web dashboard with buttons and toggles, and passes messages to devices over MQTT. The ESP32 and the dashboard never talk directly, they both talk to Adafruit IO, so control works from anywhere with internet.

Basic concept of MQTT

MQTT is a lightweight publish/subscribe messaging protocol designed for small devices and unreliable networks. Instead of a client asking a server for data (HTTP), clients keep one connection open to a broker. Messages are sent to named topics, and the broker delivers each message instantly to every client subscribed to that topic. It supports three Quality-of-Service levels (0 at most once, 1 at least once, 2 exactly once).

Publisher, subscriber, broker and topic/feed

RoleIn this project
PublisherThe Adafruit IO dashboard toggle block, which publishes ON or OFF
BrokerAdafruit IO’s MQTT server (io.adafruit.com)
SubscriberThe ESP32, which listens for new values and switches the relay
Topic / feedFeed named bulb, which is the MQTT topic <username>/feeds/bulb

A feed is both the topic that messages travel on and the place where the latest values are stored, so the ESP32 can also read the last value when it reconnects.

Wiring diagram: ESP32, relay and mains

 Only the LIVE wire is switched. Neutral is NOT switched.
Safety. 230 V mains can kill. The relay separates the ESP32 (3.3 V logic) from the mains side. Only the live wire goes through the relay; neutral goes straight to the bulb. All logic was first tested with the relay unconnected to mains, and the relay starts in the OFF state.

Adafruit IO account, dashboard and feed configuration

  1. Create a free account at io.adafruit.com. The username and AIO key are under My Key. Keep the key private.
  2. Create a feed called bulb (Feeds → New Feed).
  3. Create a dashboard (Dashboards → New Dashboard) and add a Toggle block connected to the bulb feed with ON value ON and OFF value OFF.
  4. Put the username and key in the sketch (never in a public repository).

Communication flow between ESP32, MQTT and Adafruit IO

Dashboard toggle ──publish "ON"──▶  Adafruit IO (MQTT broker)
                                         │  topic: <username>/feeds/bulb
                                         ▼  deliver to subscribers
                                      ESP32 (subscriber, callback handleBulbCommand)
                                         │  digitalWrite(GPIO26, LOW)
                                         ▼
                                   Relay coil energised → contact closes
                                         │
                                         ▼
                              230 V circuit complete → bulb ON

Latency from toggle to bulb was under one second in testing.

Complete ESP32 source code

Show task2_task3_mqtt_relay.ino
// Tasks 2 & 3 - ESP32 subscribes to an Adafruit IO feed (MQTT) and drives a relay.
// Task 2: the feed is changed from the Adafruit IO dashboard toggle.
// Task 3: the same feed is changed by an IFTTT webhook (Google Assistant voice command).
// The ESP32 code is identical for both - only the publisher changes.
// Library: "Adafruit IO Arduino" (+ Adafruit MQTT Library)
#include <AdafruitIO_WiFi.h>

#define IO_USERNAME "YOUR_ADAFRUIT_USERNAME"
#define IO_KEY      "YOUR_ADAFRUIT_IO_KEY"      // never commit your real key
#define WIFI_SSID   "YOUR_WIFI_SSID"
#define WIFI_PASS   "YOUR_WIFI_PASSWORD"

AdafruitIO_WiFi io(IO_USERNAME, IO_KEY, WIFI_SSID, WIFI_PASS);
AdafruitIO_Feed *bulb = io.feed("bulb");        // MQTT topic: <username>/feeds/bulb

#define RELAY_PIN 26
#define RELAY_ON  LOW      // relay module is ACTIVE-LOW: LOW energises the coil
#define RELAY_OFF HIGH

void handleBulbCommand(AdafruitIO_Data *data) {
  String command = data->toString();
  command.trim();
  command.toUpperCase();

  if (command == "ON" || command == "1") {
    digitalWrite(RELAY_PIN, RELAY_ON);
    Serial.println("RELAY: ON -> bulb powered");
  } else if (command == "OFF" || command == "0") {
    digitalWrite(RELAY_PIN, RELAY_OFF);
    Serial.println("RELAY: OFF -> bulb disconnected");
  }
}

void setup() {
  Serial.begin(115200);
  delay(1000);

  pinMode(RELAY_PIN, OUTPUT);
  digitalWrite(RELAY_PIN, RELAY_OFF);           // start with the bulb OFF (fail-safe)

  bulb->onMessage(handleBulbCommand);           // callback for incoming MQTT messages
  io.connect();
  while (io.status() < AIO_CONNECTED) { Serial.print("."); delay(500); }
  Serial.println("\nAdafruit IO connected! Listening for commands...");

  bulb->get();                                  // fetch the last stored value on start-up
}

void loop() {
  io.run();                                     // keeps the MQTT connection alive
}

Explanation of the important code sections

SectionWhat it does

io.feed("bulb")Binds the program to the bulb feed (the MQTT topic)
onMessage(handleBulbCommand)Registers a callback that runs whenever a new message arrives
handleBulbCommand()Trims and upper-cases the text, then sets GPIO26 to RELAY_ON or RELAY_OFF
RELAY_ON = LOWThe relay board is active-LOW, so LOW energises the coil

Problems encountered during MQTT / cloud setup, and solutions

ProblemCauseSolution
Bulb behaved backwards (HIGH switched it OFF)The relay module is active-LOW. I read the datasheet and found this while testing at low voltage before touching mainsDefined RELAY_ON as LOW and RELAY_OFF as HIGH, and used those names everywhere
Bulb could switch on at resetPin floats or defaults while the board startsSet the pin to OFF first in setup()
Commands sometimes ignoredText from the dashboard had different case or spacingTrim and upper-case the payload; accept 1/0 too
Slow responseLatency adds up across Wi-Fi, broker and callbackKept the connection persistent instead of reconnecting

Learning reflection

  • Publish/subscribe keeps a persistent connection and pushes messages instantly, unlike HTTP polling.
  • Cloud platforms let control work from anywhere, but credentials and keys must be kept private.
  • High-voltage work needs isolation (the relay) and staged testing: logic first at low voltage, mains last.
Reflection. Moving from a local web server to a cloud broker was the biggest step so far. It forced me to think about each hop (Wi-Fi, broker, callback) as part of the delay the user feels.
